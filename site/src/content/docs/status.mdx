Every capability on this site carries one of three labels:

- <span class="tag tag-built">Built</span> in the code on `dev` today.
- <span class="tag tag-partly">Partly built</span> a working piece exists, but not the full idea.
- <span class="tag tag-vision">Vision</span> not built. A direction, not a promise.

## The bigger ideas

| Idea | State | What exists now |
|---|---|---|
| Workflow-first, agent is one node | <span class="tag tag-built">Built</span> | Eleven node types; agents are one of them |
| One workflow, several execution modes | <span class="tag tag-partly">Partly built</span> | `condition` plus agent `workspace` checkout plus harness executors. No hosted or container sandbox provider yet |
| Provider independence | <span class="tag tag-partly">Partly built</span> | Anthropic, OpenAI, Copilot per profile; `name: default` per server. Not capability-based |
| Capability-based model routing (`model: auto`) | <span class="tag tag-vision">Vision</span> | None |
| Portable agents (one contract reused across workflows and providers) | <span class="tag tag-partly">Partly built</span> | Versioned profiles, and a Library of reusable MCP servers, agents, skills and commands. No standalone agent registry |
| MCP as a first-class runtime primitive | <span class="tag tag-partly">Partly built</span> | MCP tools through the gateway with ledger and policy; remote Streamable HTTP connections; gateway bridged into harnesses. Health, latency and cost metadata pending |
| Capability resolution (`requires: issue-management`) | <span class="tag tag-vision">Vision</span> | Tools are registered by name and revision |
| Knowledge as a uniform interface | <span class="tag tag-partly">Partly built</span> | Datasets with hybrid retrieval and citations. Git, MCP resources, databases and web are not sources yet |
| Token optimization as part of execution | <span class="tag tag-partly">Partly built</span> | See [Cost and token control](/features/cost/) |
| Result caching, savings reporting | <span class="tag tag-vision">Vision</span> | Only measured cost is reported; a savings figure needs a defined baseline per workflow |
| One graph for chat, automation and coding | <span class="tag tag-partly">Partly built</span> | CLI, API, schedule and web entry points. No web chat or webhook triggers yet |
| Capability Graph | <span class="tag tag-vision">Vision</span> | The run plan already evaluates requirements against executor capabilities, which is the seed |
| Workflows exposed as MCP tools | <span class="tag tag-vision">Vision</span> | None |

## Known limits today

<Aside type="caution">
- Workers are supported on **Linux only**. The installer is a bash script.
- The macOS install has **not been tested on a Mac**, and `limits.memory_mb` is refused there (no `prlimit`).
- Native Windows local mode is experimental. OpenCode steps on native Windows are new and not yet checked by a live run.
- The alpha embedder for knowledge is lexical-hash, not a neural model.
- The Codex executor adapter is experimental and off by default. OpenCode 2 is a preview, off by default.
- The 80/100 confidence bar is enforced per finding but **not yet measured** against a labelled set.
</Aside>

## Next steps toward the vision

1. Capability fields on profiles (`capability`, `strategy`) resolved by a simple router, with the choice recorded in the run plan.
2. Tool metadata (permissions, health, latency, cost) in the registry.
3. A savings report with an explicit per-workflow baseline.
4. Web chat and webhook entry points into the same runtime.
5. A container or hosted sandbox provider for coding steps.
6. Capability resolution (`requires:`), then the Capability Graph on top of the run plan.
