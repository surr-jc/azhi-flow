Agents retry. Processes crash. Without care, that means two Slack posts, two issues or two comments. Every tool
call in Azhi passes through the **gateway**, which keeps an **action ledger**.

## One logical action, many attempts

Each external write is a logical **action** with a stable id derived from the run, node, tool, the intended
operation and an ordinal. A retry of the same operation computes the **same id**, so it finds the earlier
action instead of creating a second one. Changing the operation produces a new id.

## States

```text
planned → dispatched → confirmed
                    ↘ failed            (the target definitely did not apply it)
                    ↘ outcome_unknown   (we cannot tell)
```

Every transition is recorded and **fenced by the attempt generation**: a stale attempt can never commit after a
newer one took over.

## Effect classes decide what recovery may do

If a previous attempt ended after sending but before recording a receipt, the action becomes `outcome_unknown`.
What happens next depends on the tool's declared effect class.

| Effect class | Recovery |
|---|---|
| `write-idempotent` | Resend with the same idempotency key |
| `write-dedupable` | **Look the write up on the target by its dedupe key.** If it is found, mark it confirmed and reuse the receipt. If not, resend |
| `write-unsafe` | **Stop.** An operator must reconcile it before any retry. Azhi does not guess |

For Slack, that lookup is how a fresh gateway finds the message a crashed one had already posted.

## Across resumes

A resumed run is a new run, so its actions have their own ids. If the same step reaches the same operation and the
run it continues left that write `dispatched` or `outcome_unknown`, the resumed run does not start from nothing:

| Effect class | Recovery in the resumed run |
|---|---|
| `write-idempotent` | Resend with the **original** idempotency key |
| `write-dedupable` | Look the write up by the **original** dedupe key. If it is found, reuse the receipt. If not, resend under that key |
| `write-unsafe` | **Stop** and name the earlier action. It goes ahead once that action has a settled state |

This follows a chain of resumes back to the first send. These writes can still repeat on resume:

- **Changed arguments.** A different operation is a different action, as in any run. An agent that words a comment
  differently on the rerun, or a step upstream that produced new data, makes a new write.
- **Writes already confirmed in a step that failed afterwards.** That step runs again and its writes go out again,
  including earlier items of a `parallel` step or tool `loop`. Choosing a step with `from_node` repeats its writes the
  same way. `azhi` warns about steps that succeeded; it does not see confirmed writes inside a failed one.
- **Writes inside a subworkflow.** A rerun step starts a new child run, which is not linked to the earlier child.
- **Two resumes of one run at the same time.** Both can miss the lookup and send, though under the same key.

The target also has to honour the key for that long: an idempotency key the target has already forgotten protects
nothing, and the ledger cannot tell. MCP tools receive no key at all, so a `write-idempotent` MCP tool has to be
safe to repeat by itself, in a retry as much as in a resume.

## Proof, not a promise

The alpha demo kills the gateway right after Slack accepted the post. A fresh gateway finds the message by its
dedupe key. Exactly one message exists, and the ledger line shows how.

```bash
npm run demo            # check 4: crash mid-post
npx azhi inspect <run>  # state, flags, attempts, approvals, usage, context manifests and the ledger
```

The test suite injects crashes at named points (after planned, after dispatched, after sent) by killing the
process, the same as a power loss.

## Related behavior

- **Loops**: each iteration has its own ledger ordinal, so writes inside a loop are deduplicated per iteration.
- **Sticky comments**: the PR review tool is registered with a sticky marker, so a later run edits the earlier
  review comment instead of adding another.
- **Alerts**: writes left in `outcome_unknown` raise an alert in Mission Control.
- **Test runs**: `azhi test-node` mocks writes, so nothing reaches the ledger.

<Aside type="caution">
The ledger covers writes that go **through the gateway**. MCP servers that a coding-harness profile starts
itself do not, and the run plan marks them *unobservable*.
</Aside>
