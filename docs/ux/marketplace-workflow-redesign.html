Azhi Flow · Mission control UX

Marketplace and workflow redesign

A plan for making every workflow readable before anyone runs it: what each step does, what each setting means, and what must be set up first. It is built on data the app already has, with three distinct directions, each shown as screen mockups using the product's own colors, type and real example workflows.

Step names, settings, tools, secrets and help text in the mockups come from the bundled examples and stepHelp.ts. Repository names, counts and set/missing states are examples.

Section 1

What exists today

I went through every page and component under web/src that touches the marketplace, workflows, datasets, tools and portable assets. The building blocks for a clear UX are already in the code: stepHelp.ts has a plain-language explanation for every step type and every setting, a one-sentence reading of each configured step, and the effect each step has outside Azhi. Most of that help appears only inside the editor's side panel, so someone browsing or installing a workflow never sees it.

Section 2

Rules all three directions share

The directions differ in layout and interaction. They agree on what a person must be able to learn about any step, anywhere it appears: in the marketplace, on the workflow page, in the editor and on a run.

What it doesThe step sentence, e.g. "After pr finishes, opencode runs correctness-reviewer@1…"
What it readsWhich inputs and earlier steps feed it, as links.
What it changesWrites, messages and waits, in the attention color.
What limits itTimeout, tool calls, cost, retries, guard rules.

Every setting shows its meaning

Setting name, current value, one plain sentence of meaning, and where the value comes from. Never a bare key and value.

FIELD_HELP · helpFor() · sourcesOf()

One step component everywhere

A single StepCard and ConfigRow, used by the marketplace, workflow page, editor and run page, so a step always reads the same.

keySettings() · sentenceOf() · TYPE

Readiness before action

Show what is missing (secrets, settings, repos, run-plan blockers) before the Install or Run button, and say which steps need it.

secrets[].set · settings[].value · plan.blockers

Effects use status color only

Reads are green, writes and messages amber. Step types stay neutral, keeping the app's rule that color always means status.

effectsOf() · tool.effect

Stages, not just a graph

Group steps by dependency depth into named stages (Read, Review, Decide, Act). The order is real, so numbering it is honest.

layout() longest-path layers
A Direction A

Guided recipe

Every workflow reads like a recipe: numbered stages from top to bottom, each step a row that expands into a config sheet with a meaning beside every setting. Installation becomes a five-step wizard that ends only when everything is ready. It suits people who are new to Azhi and arrive from the marketplace.

Recommendation

Build Direction A as the default experience, and make the workflow page switchable between A's stage view and B's canvas with inspector, since the canvas already exists and authors will want it. Use C's table pattern for Tools, Datasets and the marketplace's optional table view, where scanning matters more than storytelling.

All three rest on the same two new components, StepCard and ConfigRow, so starting with A does not close off B or C later.

Build plan

Data gaps and phases

Most of what the mockups show is already in the client. Four things need a small server change; everything else is front-end work.

Marketplace steps are hard-codedStep count, category and "works with" live in a META map in Examples.tsx. GET /v1/examples should return nodes: [{ id, type, description, deps }] from the workflow it already parses in src/api/examples.ts, plus a category field in the workflow file.
Secrets have no description or "used by"The API returns only { name, set }; the explanations sit in YAML comments. Add description to secrets: in azhi.config.yaml, and compute used_by from each tool's credential and each agent's workspace.credential.
Settings do not say where they are usedCompute which step settings reference each {{setting}} (for example slack_channel → config.channel → notify.destination) and return it with the setting.
No reverse index for datasets and tools"Used by" needs a lookup over published versions: GET /v1/datasets/:name/usage and a used_by field on GET /v1/tools.
Phase 1Foundations
Add StepCard, ConfigRow, StepStrip, EffectChip and ReadinessList to web/src/ui.tsx, built on stepHelp.ts. Add a stagesOf(nodes) helper that reuses the canvas's longest-path layering and names stages. Make the server changes above.
Phase 2Marketplace
Rebuild Examples.tsx: cards with step strips and setup cost (A1), a "how it works" page using stages, and the set-up wizard (A3) that reuses AllowedRepos, SecretRow and CopilotLogin. Remove META.
Phase 3Workflow page
Restructure WorkflowPage in Workflows.tsx into the stage view with a side rail (A2), with a toggle to canvas plus inspector (B2). Move Files, Schedule and the run plan into tabs. Add description, step strip and readiness to the workflows list.
Phase 4Editor and runs
Use ConfigRow inside StepForm in Editor.tsx and in the run page's step drawer, so a step reads identically when browsing, editing and debugging a run.
Phase 5Catalog
Datasets with the lifecycle row and "used by" (A4), Tools as the C4 table with accepted fields, and kind-specific forms in Assets.tsx to replace the raw JSON textarea.
