Three new ways to design the workflow experience

Round 1 stayed close to today's page structure. These three ideas change the structure. One builds on your suggestion (canvas, a workflow settings dock, and a drawer or popup per step), and two take different routes to the same goal: a workflow you can read, understand and set up without guessing.

Step names, settings, tools, secrets and help text come from the bundled pr-review example and stepHelp.ts. Repository names, counts and set or missing states are examples.

Shared foundation

Two levels of configuration

Your suggestion of a global setting plus a per-step panel matches how the data is already shaped. A workflow file has settings that belong to the whole workflow, and settings that belong to one step. Today both are mixed into long panels. Splitting them is the main structural fix, and all three directions use it in different ways.

Workflow level (set once, applies to every step)

  • Inputs: what a person provides when starting a run (repo, pr, post).
  • Config values: install settings such as slack_channel.
  • Trigger and schedule: manual, or cron with a timezone.
  • Secrets and credentials, with which steps use each.
  • Connections: allowed repositories, tools registered, MCP servers.
  • Datasets and portable assets attached.
  • Version, signature and run plan: blockers and warnings.

Step level (changes what one step does)

  • What it does: the sentence from sentenceOf().
  • Type settings: profile, executor, workspace, arguments, route table.
  • Data in and out: which steps and inputs feed it, and the output shape.
  • Effects: reads, writes, sends, waits for a person.
  • Safety: guard rule, approval role, expiry.
  • Limits: timeout, retries, tool calls, cost.

Every setting in either list is shown the same way everywhere: its name, its value, a sentence that says what it means, and where the value comes from (an input, an earlier step, a config value, a secret, or the workflow file).

D Direction D

Workbench: canvas, settings dock, step drawer

This is your suggestion worked out. The canvas is the page. A dock on the left holds the workflow-level settings, each as a one-line summary that opens a larger popup. Clicking a step opens a drawer on the right with its sentence and settings. A step with a lot of configuration, such as an agent harness, has an Expand button that opens a full popup. The marketplace uses the same pieces in a "quick look" popup, so a workflow looks the same before and after you install it.

E Direction E

Living document: the sentence is the form

A workflow is shown as a short document, not a diagram or a settings panel. Each step is a sentence with its settings as inline fields, in the way sentenceOf() already writes them. Click a field and a small popover opens with the control and its meaning. Margin notes beside each step list what it reads, changes and is limited by. The same document can be switched to show the last run, with results next to each step.

Best for
People who are not engineers, reviewers, approvers
Core interaction
Read top to bottom; click a field to change it
Reuses
sentenceOf, helpFor, FIELD_HELP, SchemaFields, Coverage

F Direction F

System map: lanes and lenses

The workflow is drawn as lanes, one per system it touches (People, GitHub, agents, Azhi logic, Slack), with time running left to right. This answers the question people ask first, "what does this touch and where?", before they read any step. A lens switch re-labels the same map for one concern at a time: Flow, Access, Limits or Data. Clicking a step opens a shelf under the map, in place, instead of a drawer.

Best for
Admins, security, anyone judging risk
Core interaction
Change the lens; click a step to unfold its shelf
Reuses
effectsOf, tool effect and credential, plan.controls, layout()

Recommendation

Build D first. It is your idea, it is closest to the code you have, and it fixes the biggest problem (settings scattered across panels) with the least new surface. Its drawer and popups would use the ConfigRow component from round 1, so the earlier work still applies.

Add E's Plan/Last run switch to D's drawer, since showing planned limits next to real usage is useful and cheap once run data is loaded.

Treat F's Access lens and Connections page as a later governance feature. They need the most new work, but they are the only designs that answer "what can this touch?" across all workflows.

Step 1Foundations
Group the workflow-level settings into one WorkflowSettings list (inputs, config, trigger, secrets, connections, datasets, limits, files) and one reusable popup shell. Add used_by for secrets, tools and datasets on the server.
Step 2Workbench
Rebuild WorkflowPage as D1 and D2: dock, canvas, drawer. Reuse the editor's rows for the drawer's Settings tab so reading and editing share code.
Step 3Marketplace
Quick-look popup (D4) using the same dock summary and drawer. Remove the hard-coded META map by returning nodes from /v1/examples.
Step 4Plan and run
Add the Plan / Last run switch (E3) inside the drawer and on cards.
Step 5Governance
Access and Limits lenses on the canvas, then the Connections page (F4).
